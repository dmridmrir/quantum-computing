# Tesseract-PIM: Offloading Quantum Tesseract Decoding to UPMEM PIM

## Overview

This project offloads performance-critical work from the Tesseract quantum
error-correction decoder to UPMEM Processing-in-Memory (PIM) Data Processing
Units (DPUs).

Tesseract uses an A*-style search over detector error models. This repository
provides two DPU execution paths:

1. **Candidate-evaluation offload**: the CPU retains the A* search, priority
   queue, pruning, and termination logic, while DPUs evaluate batches of
   heuristic candidates.
2. **DPU-resident A* search**: a DPU executes the heap, chain arena, sibling
   evaluation, and search loop for one syndrome, returning either an error
   chain or a CPU-fallback status.

The default configuration assigns one syndrome to one DPU. Sixteen tasklets
cooperate inside each DPU, while multiple DPUs process independent syndromes in
parallel. The tasklet count remains configurable for controlled experiments.

The repository supports three main evaluation modes:

1. **Throughput and scale-out evaluation**: measures CPU-only and hybrid
   CPU+DPU decoder throughput, then evaluates scaling across DPU pool sizes.
2. **Power and energy evaluation**: combines a Windows RAPL measurement of the
   CPU baseline with a literature-based UPMEM power model.
3. **DPU utilization evaluation**: reconstructs FCFS scheduling from recorded
   resident-search attempts to estimate active-DPU occupancy at different DPU
   pool sizes.

All DPU cycle measurements in this project are obtained with uPIMulator, not
physical UPMEM hardware. uPIMulator does not measure electrical power, and the
DPU utilization results are scheduling-model estimates rather than physical
hardware telemetry.

## Repository Layout

- `simulator/tesseract_msc_bench/`: benchmark drivers, DPU kernels, traces,
  workloads, and analysis scripts.
- `simulator/tesseract_msc_bench/uPIMulator/benchmark/TESSERACT/`: candidate-
  evaluation DPU kernel and host integration.
- `simulator/tesseract_msc_bench/uPIMulator/benchmark/TESSERACT_ASTAR/`:
  DPU-resident A* kernel.
- `simulator/tesseract_msc_bench/upmem_sdk/`: bundled UPMEM compiler and runtime
  used by the reproducible WSL/Linux build.
- `third_party/tesseract-decoder/`: pinned CPU reference decoder and trace
  producer.
- `third_party/magic-state-cultivation/`: pinned source used to reproduce the
  magic-state-cultivation workload.

Generated build directories, experiment results, large workloads, and local
analysis reports are excluded from version control and are regenerated by the
scripts when needed.

## Third-Party Software

### uPIMulator

This project uses uPIMulator, a cycle-level performance simulator for UPMEM PIM
architectures.

- **GitHub repository:** <https://github.com/VIA-Research/uPIMulator>
- **Reference paper:** B. Hyun et al., "Pathfinding Future PIM Architectures by
  Demystifying a Commercial PIM Technology," *2024 IEEE International
  Symposium on High-Performance Computer Architecture (HPCA)*, 2024.

### Tesseract Decoder

The CPU reference decoder is based on the upstream Tesseract project.

- **GitHub repository:** <https://github.com/quantumlib/tesseract-decoder>

The third-party projects remain the work of their respective authors. Local
changes in this repository add trace generation, live DPU integration, and the
DPU-resident execution path used by the experiments.

## Prerequisites

### 1. Operating System

Linux or Windows Subsystem for Linux (WSL) is required. The bundled UPMEM SDK
contains Linux executables and cannot be run directly from Windows PowerShell.

### 2. Install System Dependencies

```bash
sudo apt update
sudo apt install -y \
  build-essential libgomp1 cmake ninja-build python3 coreutils gawk grep sed
```

### 3. Check Go

Go 1.21.5 or newer is required.

```bash
go version
```

## Getting Started

Open a Linux or WSL terminal and enter the benchmark directory. Quote the path
because the project directory may contain a space.

```bash
cd "/path/to/tesseract offloading/simulator/tesseract_msc_bench"
```

Run the synthetic candidate-offload smoke test:

```bash
bash scripts/build_and_run.sh 16 64 256 512 42 16
```

The arguments are:

```text
tasklets candidates detectors errors seed q_bits
```

A successful run ends with:

```text
TESSERACT uPIMulator smoke run passed
```

To replay the checked-in minimal trace instead of a synthetic workload:

```bash
TESSERACT_TRACE=traces/example_v1.json \
  bash scripts/build_and_run.sh 16
```

## Running Experiments

Unless noted otherwise, run the evaluation commands below from
`simulator/tesseract_msc_bench`.

### Mode 1. End-to-End Throughput and Scale-Out Evaluation

Compare CPU-only decoding with the live hybrid CPU+DPU path using the included
MSC fixture:

```bash
bash scripts/run_live_dem_comparison.sh \
  workloads/msc_grafted_d3_d7/model.dem \
  workloads/msc_grafted_d3_d7/syndromes.01 \
  workloads/msc_grafted_d3_d7/observables.01 \
  results/live_msc_grafted_d3_d7 \
  0 64 16 16 8 64
```

The trailing values select the shot range, tasklets per DPU, fixed-point
precision, CPU worker count, and maximum in-flight DPUs.

For a measured scale-out sweep followed by extrapolation to 2,560 DPUs:

```bash
bash scripts/run_scaleout_extrapolation.sh \
  workloads/msc_grafted_d3_d7/model.dem \
  workloads/msc_grafted_d3_d7/syndromes.01 \
  workloads/msc_grafted_d3_d7/observables.01 \
  results/scaleout \
  64 4,8,16,32,64 16 8,16 2560
```

Reported speedup is the ratio of full hybrid system throughput to the matching
CPU-only full-system throughput. DPU kernel throughput alone is not reported as
end-to-end decoder throughput.

### Mode 2. Power and Energy Evaluation

The CPU baseline is measured with Windows RAPL counters while the CPU decoder
runs inside WSL. Run the following command from Windows PowerShell:

```powershell
cd "C:\path\to\tesseract offloading\simulator\tesseract_msc_bench"
.\scripts\run_cpu_power_baseline.ps1 -NumShots 100000 -CpuThreads 16
```

This measurement requires the large
`workloads/msc_grafted_d3_d7_100m` dataset. Large generated workloads and
measurement results are intentionally not stored in Git. The script writes
`power_samples.csv` and `power_summary.json` under `results/power/<run-name>`.

After generating the matching throughput/timing model, combine it with the CPU
power summary:

```bash
python3 scripts/power_model.py \
  --timing-model results/paper_dpu_validation/timing_model_paper.json \
  --cpu-power-summary results/power/<run-name>/power_summary.json \
  --cpu-power-transfer-note "Describe why the power run matches the timing model" \
  --output-dir results/power/model
```

The model generates `energy_comparison.csv`, `energy_comparison.json`, and
`ENERGY_REPORT.md`. CPU power can be measured with RAPL, but DPU power is based
on externally sourced DIMM/server power values. Therefore, the DPU result is a
conditional energy model, not a measured wall-power result from this workload.

### Mode 3. DPU Utilization Evaluation

Reconstruct compute-only FCFS scheduling for the completed nine-million-shot
resident-search dataset:

```bash
node scripts/analyze_9m_dpu_occupancy.js
node scripts/analyze_9m_dpu_scale.js
```

The occupancy analysis reports active-DPU counts and the mean active-DPU
fraction for a 2,560-DPU pool. The scale analysis repeats the reconstruction for
128, 256, 512, 1,024, 2,048, and 2,560 DPUs. These scripts require the generated
nine-million-shot chunk logs, resident timing model, and cycle samples under
`results/`; those artifacts are not tracked by Git.

For a checked-in trace, inspect the amount of candidate-level DPU parallelism
without the large result set:

```bash
python3 scripts/analyze_trace_parallelism.py \
  traces/official_msc_grafted_d3_d7.json
```

Utilization values from these scripts are modeled scheduling occupancy. They
must not be reported as physical DPU utilization or simulator-measured hardware
occupancy.

## Notes

- One syndrome is assigned to one DPU in the default execution model.
- Sixteen tasklets cooperate on the syndrome within that DPU.
- Independent DPUs process independent syndromes and do not communicate with
  each other.
- The DPU hot path uses integer and fixed-point arithmetic; logarithms and
  probability conversion remain on the host.
- Candidate-evaluation and DPU-resident A* results are separate measurements
  and must not be mixed when reporting performance.
- Generated files under `results/`, simulator build directories, and large
  workloads are intentionally not tracked by Git.
