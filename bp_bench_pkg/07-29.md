# 07-29

## 문서 범위

이 문서는 현재 워크스페이스에 있는 cooperative layered BP의 v1과 v2 코드만 정리한다. 실험 결과, 논문 문구, EC2 업로드 절차, 과거 구현은 포함하지 않는다.

## 공통 구현 구조

- 대상 코드는 `[[144,12,12]]` Bivariate Bicycle qLDPC 코드이며 Tanner graph의 크기는 variable node 144개, check node 72개, edge 432개이다. Check degree는 6, variable degree는 3이다.
- 두 버전 모두 normalized/modified Min-Sum 계열의 horizontal-layered 갱신을 사용한다. 한 check를 갱신하면 계산된 check-to-variable 메시지와 posterior 상태가 같은 iteration의 뒤쪽 check 계산에 즉시 반영되는 Gauss--Seidel 방식이다.
- 72개 check는 같은 색 안에서 variable node가 겹치지 않도록 세 그룹으로 분할되어 있다. 실행 순서는 `1 -> 2 -> 0`이며, 각 색의 계산이 끝날 때 barrier로 동기화한다.
- 현재 실험 설정은 DPU 하나의 11개 tasklet이 syndrome 하나를 공동으로 디코딩하는 구조이다. 각 tasklet이 syndrome 하나를 독립적으로 처리하는 구조가 아니다.
- Syndrome은 MRAM에서 WRAM으로 읽고, 반복해서 사용하는 메시지와 posterior 상태는 디코딩 중 WRAM에 둔다. 마지막 posterior만 MRAM 출력 영역으로 기록한다.
- 반복 횟수는 고정되어 있으며 early stopping은 사용하지 않는다.
- DPU 커널 한 번은 X 또는 Z 중 한 component의 syndrome을 처리한다. 전체 CSS decode의 X+Z 값이 필요한 실행 스크립트에서는 두 component를 직렬 처리한 값으로 계산한다.
- Tanner graph와 coloring 정보는 각각 `uPIMulator/benchmark/BPMS/support/bb144_pcm.h`와 `uPIMulator/benchmark/BPMS/support/bb144_colors.h`에서 공통으로 사용한다.

## v1

### 핵심 커널

`uPIMulator/benchmark/BPMS/dpu/task_layered.c`

- `NR_TASKLETS=11`만 허용하며, 11개 tasklet 전체가 하나의 shared decoder state를 갱신한다.
- 각 색에 속한 check들을 tasklet ID 기준 stride 방식으로 나누어 처리한다.
- 모든 tasklet이 공유하는 주요 WRAM 상태는 다음과 같다.
  - `shared_c2v[432]`: check-to-variable 메시지, `int32_t`
  - `shared_lambda[144]`: 누적 posterior 상태, `int32_t`
  - `shared_post[144]`: MRAM으로 내보낼 최종 posterior, `int16_t`
  - `shared_syn[72]`: 입력 syndrome
- 초기화 시 `lambda`를 channel prior로 채우고 모든 `c2v`를 0으로 만든다.
- Check 갱신에서는 target edge의 이전 메시지를 누적 상태에서 제외하여 variable-to-check 메시지 `q`를 만든다.
- Check의 syndrome bit와 입력 메시지들의 부호로 출력 부호를 계산하고, 최소값과 두 번째 최소값으로 target edge를 제외한 Min-Sum 크기를 계산한다.
- 정규화 계수는 `alpha=3/4=0.75`이며 shift/add 연산으로 적용한다.
- Damping은 사용하지 않는다. 새 메시지는 계산 직후 `c2v`와 `lambda`에 반영된다.
- 내부 `q`, `c2v`, `lambda`는 `int32_t` 범위를 사용하며 check별 갱신 중에는 `int16_t` saturation을 하지 않는다. 모든 iteration이 끝난 뒤 외부로 내보내는 `shared_post`만 `int16_t` 범위로 clamp한다.
- 커널 소스의 `decode(tid, 889, 2)`는 기본 실행값이다. v1 phase1 스크립트가 각 실험점의 prior와 iteration 수로 이 호출 상수를 패치한 임시 소스를 빌드한다.

### v1 실행 코드

- `run_bp_increase_layered_phase1.sh`: p와 iteration 조합별 DPU 커널 빌드·시뮬레이션 및 CPU--DPU posterior 일치 검증
- `run_bp_increase_layered_phase2.sh`: v1과 동일한 arithmetic 및 color 순서를 사용하는 CPU 기준 구현으로 throughput과 LER 계산
- `bp_tail_layered_phase1.sh`: cooperative v1 DPU cycle sample 수집. 기본 iteration 범위는 1부터 5까지이다.
- `bp_tail_layered_phase2.sh`: CPU latency 측정과 DPU cycle 변환 후 p/iteration별 tail-latency 통계 출력
- `run_bp_increase_layered.sh`, `bp_tail_layered.sh`: 해당 phase 실행을 묶는 wrapper

## v2

### 핵심 커널

`uPIMulator/benchmark/BPMS/dpu/task_layered_v2.c`

- `BP_GROUP_SIZE`개의 tasklet이 하나의 syndrome을 처리하는 group 구조를 지원한다. 현재 스크립트는 `NR_TASKLETS=11`, `BP_GROUP_SIZE=11`로 빌드하므로 group은 하나이고 11개 tasklet이 syndrome 하나를 공동 처리한다.
- Group별 WRAM 상태는 다음과 같다.
  - `shared_c2v[group][432]`: check-to-variable 메시지, `int16_t`
  - `shared_post[group][144]`: 현재 posterior와 최종 출력, `int16_t`
  - `shared_syn[group][72]`: 입력 syndrome
- `q`, `c2v`, `post`를 모두 `int16_t` 범위로 saturation한다.
- 정규화 계수는 `alpha=1`이다.
- 이전 check-to-variable 메시지와 새 raw 메시지 사이에 `1/2` damping을 적용한다.
- 첫 sweep에서는 이전 `c2v`가 0이라는 조건을 이용한다. 따라서 `q=posterior`, damped message는 `raw >> 1`로 계산하며, 별도의 432-edge `c2v` 0 초기화를 생략한다.
- 마지막 iteration에서는 이후에 다시 사용하지 않을 `c2v` 저장을 생략하고 posterior만 갱신한다.
- 첫 sweep과 이후 sweep을 별도 코드 경로로 전개하지만, 두 경로 모두 동일한 세 색과 `1 -> 2 -> 0` 순서를 사용한다.
- Channel prior와 iteration 수는 소스 상수 패치가 아니라 `DPU_INPUT_ARGUMENTS.L`과 `DPU_INPUT_ARGUMENTS.num_events`에서 실행 시 읽는다.
- Group 내부에서는 색 경계마다 group barrier를 사용한다. 현재 설정은 group 하나가 전체 11개 tasklet이므로 DPU 전체가 같은 syndrome의 색 단위 진행을 맞춘다.

### v2 실행 코드

- `run_bp_increase_layered_v2_phase1.sh`: cooperative v2 DPU 시뮬레이션과 posterior 일치 검증, iteration 1부터 10까지 sweep
- `run_bp_increase_layered_v2_phase2.sh`: v2 CPU 기준 결과와 DPU 결과 결합 및 throughput/LER 출력
- `bp_tail_layered_v2_phase1.sh`: cooperative v2 DPU cycle sample 수집, iteration 1부터 10까지 sweep
- `bp_tail_layered_v2_phase2.sh`: p/iteration별 DPU tail-latency 통계 출력
- `bp_increase_layered_v2_final.c`: v2 arithmetic을 사용하는 CPU 측 throughput/LER 실행 코드
- `uPIMulator/src/assembler/prim/bpms_layered_v2_verify.go`: v2 DPU posterior 검증에 사용하는 기준 코드

## v1과 v2의 코드 차이

| 항목 | v1 | v2 |
|---|---|---|
| 현재 tasklet mapping | 11 tasklets -> 1 syndrome | 11 tasklets -> 1 syndrome |
| Layered schedule | 3-color, `1 -> 2 -> 0` | 3-color, `1 -> 2 -> 0` |
| 내부 상태 폭 | `c2v`, `lambda`는 `int32_t` | `c2v`, `post`는 `int16_t` |
| Saturation | 마지막 출력만 `int16_t` clamp | `q`, `c2v`, `post`를 매 갱신마다 `int16_t` clamp |
| 정규화 계수 | `alpha=0.75` | `alpha=1` |
| Damping | 없음 | 이전/새 메시지 사이 `1/2` damping |
| 첫 sweep | 일반 sweep과 같은 식, `c2v`를 먼저 0으로 초기화 | old `c2v=0`을 이용한 전용 경로, 전체 `c2v` 초기화 생략 |
| 마지막 iteration | `c2v`와 posterior를 모두 갱신 | 불필요한 최종 `c2v` 저장 생략 |
| prior/iteration 전달 | phase1에서 소스의 상수 패치 | runtime argument 사용 |
| decoder state 구성 | DPU 전체에 하나 | group별 하나; 현재 설정은 group 하나 |

## 코드 일치 조건

- CPU와 DPU를 비교할 때는 graph, syndrome, prior, iteration 수뿐 아니라 color 순서, saturation 위치, 정규화 계수, damping, 첫/마지막 sweep 처리까지 같은 버전의 규칙으로 맞춰야 한다.
- v1 CPU 기준 코드를 v2 DPU와 비교하거나 그 반대로 비교하면 서로 다른 알고리즘 변형을 비교하게 되므로 posterior byte-level equality의 기준으로 사용할 수 없다.
- 현재 실험 mapping을 유지하려면 v1은 `NR_TASKLETS=11`, v2는 `NR_TASKLETS=11`과 `BP_GROUP_SIZE=11`로 빌드해야 한다.
